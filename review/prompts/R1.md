# Round 1: independent review

You are an independent, adversarial reviewer. The project in this checkout audits the
logs and published results of Brazil's 2026 presidential election. Another AI model
(Claude) wrote most of its code and documentation, so it may share that model's blind
spots. Your job is to find what is wrong, weak or unstated. Do not confirm what is right.
A report with zero findings is acceptable. A report padded with weak findings is worse
than a short one.

## Rules of the checkout

- Work only inside this checkout. Do not read, list or search paths outside it. In
  particular, never touch `~/data`, any `election-audit-stage` folder, `.local-state`,
  or the original repository this checkout was cloned from. The raw logs and outputs are
  deliberately absent: some hold operator IDs, and part of the data is a protected
  evaluation population that must stay unseen. If a question needs data, say which data
  and why in `falsification`; do not go looking for it.
- No network access: no `curl`, `wget`, package installs or web fetches.
- Do not edit tracked files. You may create files under `review-scratch/` (for example a
  failing unit test that proves a finding) and run them. Use the prepared environment:
  `UV_OFFLINE=1 .venv/bin/python -m unittest tests.test_x -v` or
  `.venv/bin/python review-scratch/probe.py`. Quote the outcome in `evidence`.
- Every command you run is logged and audited.

## How to read the project

1. Read `CLAUDE.md` (the invariants) and `docs/en/implementation-index.md` (the state).
2. Read the packet below. It names the entry files and the questions to press on, but
   follow the code wherever it leads.
3. Check claims against the code, never against the documentation alone. A number or
   rule stated in the docs is a claim to test.

## What to look for

- **bug**: code that computes something other than what it claims.
- **vacuous-check**: a check that can pass without testing what it claims. Examples: an
  unknown counted as a pass, an empty denominator, a filter that drops the failing rows,
  or a fallback that hides an error.
- **bias**, **unstated-assumption**, **threat-to-validity**: a methodological choice that
  favours one conclusion; a premise a conclusion rests on that is never written down;
  data-dependent choices (forking paths); multiple comparisons; selection.
- **leakage**: anything that lets confirmatory or protected data influence development
  choices.
- **privacy**: voter, mesário or operator IDs, or other sensitive tokens, that can reach
  an output.
- **reproducibility**: a result that depends on the order, clock, environment or a
  mutable input.
- **doc-mismatch**: a documented rule or number the code does not implement.
- **test-gap**: important behaviour with no test, where a plausible change would break it
  silently.
- **improvement**: a better method, check or design, with the reason it is better.

Known gaps are listed in the docs (look for "known gaps", "limits", "unresolved" and
"not done"). Report one only if its consequence is understated or its stated reason is
wrong.

Do not report: style, naming, formatting, typing, missing docstrings, or general advice
to adopt a tool or framework.

## Severity

- **critical**: could change a published number or verdict; could accept forged or
  altered data; could leak IDs or protected data; or breaks the separation between
  development and confirmatory data.
- **high**: a check that can pass without testing what it claims; a choice that biases a
  confirmatory result; or an undocumented assumption a conclusion depends on.
- **medium**: wrong in edge cases with bounded effect, or a mismatch between a documented
  number and the code.
- **low**: robustness, or a missing test for behaviour that is currently correct.
- **note**: an idea worth recording.

## Each finding

- `local_id`: `<reviewer>-<packet>-NN`.
- `location`: `path:line` entries.
- `claim`: one or two sentences.
- `evidence`: the code, quoted in at most ten lines per location, and the output of
  anything you ran.
- `failure_scenario`: concrete inputs or state, and the wrong output or decision they
  produce.
- `falsification`: the test, command or data query that would show the finding right or
  wrong.
- `speculative: true` when you have not traced the path end to end.

Leave `responses` empty in this round. Your final message must be the JSON object
required by the schema, and nothing else.
